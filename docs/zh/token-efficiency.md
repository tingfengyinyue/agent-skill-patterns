# Token 节约策略

如何架构一个尊重 context window 限制的 agent 知识系统。

---

## 问题

每一个被知识加载消耗的 token，都是 agent 无法用于推理、工具调用和输出生成的 token。一个在 agent 开始工作前就灌入 5000 tokens 上下文的知识库是浪费的。

**目标：** 用最少的 token 开销获得最大的相关上下文。

---

## 策略 1：JSON 索引放在 Markdown 顶部——"目录"技巧

在人类可读的 Markdown 文件顶部放置一个机器可读的 JSON 块。Agent 先读压缩的 JSON（50 tokens）做过滤，然后只读匹配的完整条目。就像查字典时先看目录定位到某一页，而不是从头翻到尾。

### 模式
```markdown
# 记忆索引

## 快速召回 (JSON)

\```json
[
  {"id":"om-001","services":["payment"],"symptoms":["timeout"],"confidence":"high","hits":5},
  {"id":"om-002","services":["auth"],"symptoms":["403"],"confidence":"medium","hits":2}
]
\```

## 完整条目

### om-001: 支付超时行锁捷径
(200 tokens 的详细内容)
...

### om-002: Auth 403 token 过期检查
(200 tokens 的详细内容)
...
```

**开销分析：**
- 没有 JSON 索引：读所有条目 = 400+ tokens
- 有 JSON 索引：读 JSON (50 tokens) + 1 条相关条目 (200 tokens) = 250 tokens
- 条目越多，节省越大（线性增长）

### 什么时候用
- 有 5+ 条目的索引文件
- agent 需要先过滤再读详情的任何文件
- 记忆索引、服务目录、事件列表

## 策略 2：分层读取——先浅后深，卡住了再深入

将知识组织为详细程度递增的层次。先读最便宜的那层；只在需要时才往深处钻。

### 四个层次

```
第 0 层: 热缓存        (~100 tokens)  ← 始终读取
第 1 层: 索引/目录     (~200 tokens)  ← 热缓存没命中时再读
第 2 层: 领域页面      (~300 tokens)  ← 只读相关的那一个
第 3 层: 原始完整内容  (~500+ tokens) ← 只在深度调查时读
```

### 实现

```markdown
## 热缓存（第 0 层）
最近的上下文摘要。每次会话后更新。
包含: 最近 3 个事件、活跃告警、今天的关键指标。

## 索引（第 1 层）
所有知识页面的主目录。
包含: 页面标题、类型、日期——足以定位你需要的。

## 领域页面（第 2 层）
单个服务文档、runbook、记忆条目。
包含: 一个特定主题的完整程序性知识。

## 原始资料（第 3 层）
原始素材、完整日志、完整报告。
包含: 所有内容——只在需要精确细节时读。
```

### 读取协议

```
Agent 收到任务
  → 读热缓存（始终, ~100 tokens）
  → 够了？→ 执行
  → 不够？→ 读索引（额外 ~200 tokens）
  → 找到相关页面？→ 只读那一个（~300 tokens）
  → 还需要更多？→ 读原始资料（~500+ tokens）
```

**典型开销：** 100-400 tokens 用于上下文加载。
**最坏情况：** 1000+ tokens（仅面对全新的复杂问题）。

## 策略 3：优先级查询——先便宜后昂贵

搜索信息时，先尝试最便宜的查询。只在便宜的失败时才升级到昂贵的。

### 查询开销层级

| 优先级 | 查询类型 | Token 开销 | 确定性 |
|--------|---------|-----------|--------|
| 1 | 精确 ID 查找 (trace_id) | 低 | 高 |
| 2 | 范围过滤 (服务 + 时间) | 低-中 | 高 |
| 3 | 类别过滤 (错误级别) | 中 | 中 |
| 4 | 全文搜索 (关键词) | 高 | 低 |
| 5 | 广泛扫描 (所有最近日志) | 很高 | 很低 |

### 在 skill 中的实现

```markdown
## 查询策略

1. 有 trace_id？→ 直接用它（一条精确查询）
2. 有具体接口 + 时间？→ 范围查询
3. 有服务名 + 错误级别？→ 过滤查询
4. 只有关键词？→ 全文搜索（最后手段，警告噪声大）
```

**为什么节省 token：** trace_id 查询返回 3-5 行相关内容。广泛关键词搜索返回 100+ 行，agent 还要再花 token 来过滤——为无关内容浪费 token。

## 策略 4：结构化优于散文——表格胜过段落

对参考类材料，表格和结构化格式比散文更省 token。

### 对比

**散文版（87 tokens）：**
```
payment 服务在生产环境用 payment-logs 这个 logstore，
在测试环境用 payment-dev。auth 服务在生产环境用 auth-logs，
在测试环境用 auth-dev。gateway 在生产环境用 gateway-logs，
在测试环境用 gateway-dev。
```

**表格版（45 tokens）：**
```markdown
| 服务 | 生产 | 测试 |
|------|------|------|
| payment | payment-logs | payment-dev |
| auth | auth-logs | auth-dev |
| gateway | gateway-logs | gateway-dev |
```

**相同信息，少 48% 的 token。** 而且 agent 解析表格比解析散文更准确。

### 什么地方用表格

- 配置映射（服务 → 资源）
- 错误处理（错误 → 解决方案）
- 决策矩阵（条件 → 动作）
- 参数参考（标志 → 描述）

---

## 策略 5：增量状态优于全量重载——只处理变化的部分

追踪什么已经处理过了。只加载/处理自上次以来的差异（增量）。

### 反模式：每次全量重载

```
每次扫描: 克隆 8 个仓库 → 扫描所有文件 → 重写所有文档
开销: 10 分钟, 50,000+ tokens 的代码阅读
```

### 模式：带状态文件的增量处理

```json
{
  "payment-service": {"last_commit_sha": "abc123"},
  "auth-service": {"last_commit_sha": "def456"}
}
```

```
每次扫描:
  对每个服务:
    new_commits = git log last_commit_sha..HEAD
    如果没有 → 跳过 (0 tokens)
    如果有 → git diff last_commit_sha..HEAD -- relevant_paths/
    只更新受影响的文档章节
开销: 30 秒, 2,000 tokens 的聚焦 diff 阅读
```

**节省：** 典型运行中减少 96% 的开销。

## 策略 6：渐进式披露——只在需要时展开详情

> "渐进式披露"意味着：不要一次性展示所有内容。像一本只打开你翻到的那章的书——而不是同时打开所有章节。

Skill 本身也应该是 token 高效的。不是所有东西都需要放在主 SKILL.md 中。

### 三级加载

```
第 1 级: 元数据（始终在 context 中）     ~20 tokens
  frontmatter 中的 name + description

第 2 级: SKILL.md 正文（触发时加载）     ~200-400 tokens
  核心指令、步骤、模板

第 3 级: 参考文件（按需加载）            ~300+ tokens 每个
  详细文档、示例、Schema
  只在 skill 明确说"读取它"时才加载
```

### SKILL.md 体积指导

| 内容类型 | 建议 |
|---------|------|
| 核心指令 | 放在 SKILL.md 中（≤500 行） |
| 配置表格 | 放在 SKILL.md 中 |
| 详细 Schema | 放在 `references/schema.md` |
| 扩展示例 | 放在 `references/examples.md` |
| 工具脚本 | 放在 `scripts/`（执行它，不要读它） |

---

## 衡量 Token 效率

### 追踪指标

1. **上下文加载比：** 花在知识上的 tokens / 花在任务执行上的 tokens
   - 目标: < 30% 在知识上, > 70% 在执行上

2. **命中率：** 加载的知识中有多少比例真正被用在了响应中
   - 目标: > 80% 的加载内容在输出中被引用

3. **升级频率：** 便宜查询失败需要升级到昂贵查询的频率
   - 目标: < 20% 升级率（说明你的索引和缓存是有效的）

### 效率差的信号

- Agent 在同一会话中多次读取同一个文件
- Agent 加载了 1000+ tokens 的上下文然后只引用了其中 50 tokens
- 增量就够的时候做了全量扫描
- 索引文件只有散文（没有 JSON 快速召回块）
