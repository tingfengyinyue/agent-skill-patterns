# 知识图谱设计

知识库如何同时实现三个目标：**最小 token 开销**、**丰富的交叉引用**、**双向时序感知**。

---

## 核心问题

AI Agent 的 context window（上下文窗口）是有限的——就像一张书桌的面积。一个包含 50 份服务文档、200 条操作记忆、100 条事件记录的知识库不可能一次性全部摊开。然而 agent 需要：

1. **快速**找到正确的知识（不能把所有东西都读一遍）
2. 沿着实体间的**关联**导航（事件 → OM → 服务）
3. 理解**时间方向**（之前发生了什么 vs 下次该怎么做）

这个设计同时解决了这三个问题。

---

## 架构：是图，不是文件夹

```
                    ┌─────────────┐
            ┌──────│    服务      │──────┐
            │      │  (第 1 层)   │      │
            │      └──────┬───────┘      │
            │             │              │
      "影响"       "记录于"       "被配置"
            │             │              │
            ▼             ▼              ▼
    ┌───────────┐  ┌───────────┐  ┌───────────┐
    │   事件    │  │  Runbook  │  │   配置     │
    │  (第3层)  │  │  (第2层)  │  │  (第2层)   │
    └─────┬─────┘  └───────────┘  └───────────┘
          │                ▲
      "学到"          "晋升为"
          │                │
          ▼                │
    ┌───────────┐          │
    │    OM     │──────────┘
    │  (第4层)  │
    └───────────┘
```

知识库中的每个实体都是一个**节点**，通过有类型的**边**连接到相关节点。这不是树形结构——它是一个有环的图（OM 引用它来自的事件，而事件也引用它生成的 OM）。

---

## 亮点 1：漏斗式按需加载

> Agent 不会读取整个知识库。它先用索引过滤（开销极低），再深入读取命中的条目（按需展开）。就像查字典时先看目录定位到某一页，而不是从头翻到尾。

### 模式

Agent 按照不断扩大的同心圆读取——一旦获得足够上下文就停止：

```
开销:   ~50 tokens     ~100 tokens     ~300 tokens      ~500+ tokens
        ─────────────────────────────────────────────────────────────▶

圈 0:   JSON 索引      读取匹配的       读取完整的       读取关联的
        (仅过滤)        OM 条目          服务文档        历史事件
```

### 具体示例

任务: "payment-service 14:30 超时"

```
步骤 1: 读取 OM 索引 JSON 块                              [50 tokens]
        → 过滤: service=payment, symptoms=timeout
        → 命中: om-2026-07-01-001 (可信度: medium, 命中: 3)

步骤 2: 读取 om-2026-07-01-001.better_action              [80 tokens]
        → "先检查批量导入的 cron 任务是否在运行（14:30 启动）"
        → Agent 现在知道应该先检查什么

步骤 3: (仅在步骤 2 不够时)
        读取 payment-service.md → 定时任务章节            [150 tokens]

步骤 4: (仅面对全新问题时)
        搜索 incidents/ 中的类似历史事件                  [200+ tokens]
```

**典型场景：步骤 1-2 = 130 tokens 就解决了。**
**如果没有漏斗读取：读取整个服务文档 + 所有 OM = 2000+ tokens。**

### 为什么有效

JSON 索引像一个**目录过滤器**——让你跳过无关章节而不需要打开它们：
- 每条记忆都有索引条目（不会遗漏）
- 典型过滤能消除 80-95% 的无关条目
- 开销固定（~50 tokens），不随知识库大小增长

## 亮点 2：双向链接——任何方向都能导航

> 当 A 链接到 B 时，B 也链接回 A。不管你当前在哪个节点，都能直接找到所有相关节点——不需要扫描所有文件。

### 每条边都是双向的

当一个事件创建了一条 OM，**事件和 OM 两侧**都记录了这个关系：

```yaml
# 在事件文件中 (2026-07-15-payment-timeout.md)
lessons:
  - Created OM: om-2026-07-15-001

# 在 OM 文件中 (om-2026-07-15-001.md)
evidence:
  incidents: [2026-07-15-payment-timeout]
```

当一个服务文档列出了依赖，**下游**服务也列出了**上游**调用方：

```markdown
# 在 payment-service.md 中
## 下游（本服务调用的）
- notification-service: POST /api/notify/send

# 在 notification-service.md 中
## 上游（调用本服务的）
- payment-service: POST /api/notify/send
```

### 为什么双向链接重要

| 场景 | 需要正向链接 | 需要反向链接 |
|------|------------|------------|
| "这个事件学到了什么？" | 事件 → OM | — |
| "这条 OM 为什么存在？" | — | OM → 事件 |
| "谁在调用 payment-service？" | — | 服务 → 上游调用方 |
| "payment-service 依赖什么？" | 服务 → 下游 | — |
| "这个 runbook 还有用吗？" | — | runbook ← 晋升来源的 OM |

没有双向链接时，agent 必须**扫描所有文件**才能找到反向引用（昂贵）。有了双向链接，就是**直接查找**——无论有多少文件，耗时恒定。

### 交叉引用矩阵

```
            服务       事件       OM        Runbook    配置
服务          —       影响       相关       指导       定义
事件        被影响      —        学到       遵循        —
OM          适用于    证据        —        晋升为      相关
Runbook     针对       —        来源        —        引用
配置        配置       —         —          —         —
```

每个有值的格子意味着存在一条从任意方向都可导航的直接链接。

## 亮点 3：双向时序——过去指导未来

> OM（操作记忆）同时有一个指向过去的指针（它从哪里来）和一个指向未来的指针（下次该怎么用）。它是连接过去事件和未来决策的时间桥梁。

### 时间的两个方向

知识在系统中沿两个时间方向流动：

```
过去 ◀──────────────────────────────────────────────────▶ 未来

  事件                 OM                    Runbook
  (发生了什么)         (桥梁)                (该怎么做)
  ────────────────────────────────────────────────────────

  记录过去的      →   提炼教训给      →   晋升为
  事实                未来使用             正式流程
```

**回溯视角（取证性质）：**
- 事件记录*发生了什么*（事实、时间线、根因）
- OM 的 `context_before` 记录*哪里出了错*（走的弯路）
- OM 的 `evidence` 链接回触发事件

**前瞻视角（指导性质）：**
- OM 的 `better_action` 告诉 agent *下次该怎么做*
- Runbook 编码了*可执行的流程*
- 服务文档描述了系统的*当前状态*

### OM 是时间桥梁

操作记忆是**唯一同时存在于两个时间方向**的实体：

```
     过去                    现在                     未来
       │                      │                       │
  [事件]                 [OM 条目]                [下一个任务]
  "7-15 那天             "支付超时在               Agent 召回
   payment 超时           14-15 点之间:            OM, 先检查
   因为批量任务           先查批量 cron            cron → 30 秒
   的表锁"               时间表"                  解决问题
       │                      │                       │
       └── evidence ────────▶ │ ◀── recall ──────────┘
```

这就是为什么 OM 同时有 `evidence.incidents`（指向过去）和 `trigger.symptoms`（匹配未来）。它是连接过去事件和未来决策的时间桥梁。

### 知识生命周期——诞生、成长、退役

知识不是静态的，它有一个随时间演进的生命周期：

```
诞生                    成长                    成熟                   退役
─────────────────────────────────────────────────────────────────────────────────
事件发生           →   创建 OM            →   OM 被验证 (hits↑)   → 晋升为 Runbook
(第 3 层)              (第 4 层, low)        (第 4 层, medium)     (第 2 层)
                                                                    
                                              或者
                                              OM 被推翻            → 废弃
                                              (连续无效 2 次)        (归档)
```

**每个实体中的时间标记：**

| 实体 | 时间字段 | 用途 |
|------|---------|------|
| 服务 | `last_scan` | 这份文档最后一次与代码核对是什么时候？ |
| 事件 | `date`、时间线表 | 什么时候发生的，什么顺序？ |
| OM | `created_at`、`last_verified_at`、`hits` | 什么时候诞生、最后一次确认有用 |
| Runbook | `last_reviewed` | 这个流程还是当前的吗？ |
| 状态文件 | `last_commit_sha`、`last_scan` | 处理到了什么位置？ |

### 过期检测——自动清理

时间向前流动，知识会衰减。系统主动检测过时内容：

```
规则 1: OM 6 个月未被召回        → 标记为过期
规则 2: 服务文档 30 天未扫描     → 触发重新扫描
规则 3: Runbook 90 天未被引用    → 标记为待审查
规则 4: 事件超过 12 个月         → 归档（召回时降低优先级）
```

这防止知识库变成过时信息的坟场。

## 全景图：如何串联

给定任务 "payment-service 在 /api/order/create 返回 500"：

```
1. 感知: 提取 → service=payment, symptom=500, endpoint=/api/order/create

2. 规划 (漏斗式加载):
   ├── 读取 OM 索引 JSON (50 tokens) → 按 service + symptom 过滤
   ├── 命中: om-2026-07-01-001 (支付超时 → 检查 cron)
   ├── 读取 better_action (80 tokens)
   └── 策略: 先检查批量任务时间表，再做标准诊断

3. 执行 (图导向):
   ├── 检查 cron 状态 → 未在运行 → 不是已知原因
   ├── 沿服务图的边: payment → 下游依赖
   │   └── notification-service: 它响应正常吗？
   ├── 读取 payment-service.md (仅依赖关系章节, 100 tokens)
   └── 诊断: 下游 notification-service 超时 → 级联 500

4. 反思 (创建时间桥梁):
   ├── Q1: 走弯路了？是——先按 OM 检查了 cron，但问题在下游
   ├── Q4: "下次做 X"？是——"payment 报 500 + 下游有 notification → 先查 notification 健康状态"
   ├── 创建: om-2026-07-16-001 (新 OM, 可信度: low)
   │   ├── evidence.incidents → [今天的事件]       ← 反向链接
   │   └── trigger.symptoms → [500, order, cascade] ← 正向匹配
   └── 更新事件记录 → lessons: "Created OM om-2026-07-16-001"
```

**消耗的知识 token: ~280**
**创建的知识实体: 1 条 OM + 1 条事件记录（全部双向链接）**
**未来收益: 下次类似任务从步骤 2 开始，已有更好的策略**

## 设计原则总结

| 原则 | 实现方式 | 收益 |
|------|---------|------|
| **先读便宜的，再深入** | JSON 索引 → 匹配条目 → 关联文档 | 85% token 节省 |
| **双向链接** | 每条边存储在两个端点 | 直接查找，无需扫描 |
| **桥接过去和未来** | OM 有 evidence（过去）+ trigger（未来） | 智慧复利增长 |
| **处处追踪时间** | 时间戳、命中计数、过期规则 | 自我维护的新鲜度 |
| **图而非树** | 允许环（OM↔事件, 服务↔服务） | 自然的关系建模 |
