# 设计哲学

构建生产级 AI Agent Skill 的七条原则。

这些不是理论——它们来自一个真实运行的 AI 辅助运维平台，管理 8+ 微服务的日常事件响应、每日报表和服务监控。

---

## 原则 1：Skill 是给 Agent 的操作手册，不是给人看的文档

Skill 不是让人阅读的文档，而是给 AI Agent 的**可执行指令集**。

**实际含义：**

- 每个 skill 有明确的**触发条件**（什么话术会激活它）
- 每个 skill 有**参数类型**（接受什么输入）
- 步骤是**编号且无歧义的**（不会出现"你可以考虑试试……"）
- 输出格式是**模板化的**（agent 确切知道要产出什么）

**反模式：**
```markdown
## 概述
这个工具帮助日志分析。你可以用它来查询各种服务的日志。
构造查询时可以考虑时间范围和服务名。
```

**正确模式：**
```markdown
## 触发
当用户说 `/log-query`、`查日志`、`查询错误`

## 参数
- --service: 服务名（必填）
- --last: 时间范围（默认: 1h）
- --error: 仅过滤错误级别（标志位）

## 执行步骤
1. 解析查询意图 → 提取服务名、时间范围、关键词
2. 映射服务 → 日志源配置
3. 构建查询 → 执行 → 解析结果
4. 格式化输出 → 建议下一步操作
```

---

## 原则 2：并行优先

如果步骤之间相互独立，**必须显式标注可并行**。LLM Agent 可以并发执行操作，但前提是 skill 里明确告知哪些步骤是独立的。

**模式：**
```markdown
### 步骤 1：执行查询（可并行）

今日组（查询 1-6）和昨日组（查询 7-12）可完全并行执行。
同组内同数据源的查询也可并行。
```

**为什么重要：**
- 12 个查询串行执行需要 60 秒
- 同样的查询并行执行只需 10 秒
- Skill 必须显式声明哪些步骤是独立的

## 原则 3：错误场景 = 第一公民

每个 skill 结尾必须有一个**错误处理表**。这不是可有可无的装饰——它是防止 agent 在遇到错误时胡编恢复方案的关键。

**模式：**
```markdown
## 错误处理

| 错误 | 原因 | 处理方式 |
|------|------|----------|
| 查询超时 (>9s) | 大表全表扫描 | 重试一次；如果持续，缩小时间范围 |
| 权限被拒 | 凭证过期 | 检查 ~/.config/credentials.json |
| 无结果 | 时间范围或服务名错误 | 建议扩大范围；列出可用服务 |
| NULL 值 | 今天还没有记录 | 填充 0，标注"部分数据" |
```

**为什么用表格而不是文字：**
- Agent 可以把错误消息与表格行做模式匹配
- 每行是一个自包含的决策规则
- 没有歧义，不需要理解上下文

## 原则 4：状态感知——增量 > 全量

能只处理变化的部分，就永远不要重新处理全部。

**模式：状态文件**
```json
{
  "services": {
    "auth-service": {
      "last_commit_sha": "abc123",
      "last_scan": "2026-07-01"
    },
    "payment-service": {
      "last_commit_sha": "def456",
      "last_scan": "2026-07-10"
    }
  }
}
```

**执行逻辑：**
```
1. 读取状态文件
2. 对每个服务：检查 last_commit_sha 之后是否有新提交
3. 无新提交 → 跳过
4. 有新提交 → 仅 diff 变更路径 → 仅更新受影响的文档章节
5. 写回更新后的状态
```

**收益：**
- 8 个服务的扫描从 10 分钟降到 30 秒
- 只触碰确实需要更新的文档
- 状态文件是"什么是最新的"的唯一真相源

## 原则 5：时序性知识管理

所有知识都有时间戳，所有知识都有生命周期。

**事件记录：** `2026-07-15-payment-timeout.md`
**操作记忆：** `om-2026-07-15-001-<slug>.md`
**服务扫描：** `last_scan: 2026-07-15`

**为什么时间顺序重要：**
- 最近的事件比旧事件更有参考价值
- 操作记忆的可信度随时间演变
- 过期知识（6 个月未被召回）应标记为待审查

**生命周期状态：**
```
active → deprecated → superseded → archived
         (连续失效2次)  (被更好的替代)  (6个月未使用)
```

## 原则 6：Token 节约架构

每个加载到 context window 的 token 都是 agent 无法用于推理和输出的 token。把 context window 想象成一张书桌——摊开的参考书越多，实际工作的空间就越小。知识架构必须用最少的读取量获得最大的相关性。

**三个策略：**

### 策略 1：JSON 索引块

在人类可读的 Markdown 文件顶部放置一个机器可读的 JSON 索引：

```markdown
# 操作记忆索引

## 快速召回索引 (JSON)

\```json
[
  {"id":"om-001","task_type":["incident"],"services":["payment"],"symptoms":["timeout"],"confidence":"high","hits":5},
  {"id":"om-002","task_type":["query"],"services":["auth"],"symptoms":["not found"],"confidence":"medium","hits":2}
]
\```

## 完整条目（按需读取）
...
```

Agent 读取 JSON 块（50 tokens），过滤候选项，然后只读 1-2 条相关的完整条目（每条 200 tokens），而不是扫描所有条目（2000+ tokens）。

### 策略 2：分层读取

```
层 0: 热缓存（最近的上下文摘要，~500 字）    ← 始终读取
层 1: 索引（主目录，结构化）                 ← 热缓存未命中时读取
层 2: 领域页面（详细知识）                   ← 只读相关的那一个
层 3: 原始资料（完整文档）                   ← 只在深度调查时读取
```

### 策略 3：优先级查询

```
优先级 1: trace_id（最便宜、最确定性）
优先级 2: 具体路径 + 时间窗口
优先级 3: 错误级别 + 服务名
优先级 4: 用户 ID / 全文搜索（最贵、噪声最多）
```

永远先尝试便宜的确定性查询。只有在便宜查询失败时才升级到昂贵的广泛查询。

## 原则 7：分层处理流程——SPAR 框架

> SPAR = **S**ense（感知）、**P**lan（规划）、**A**ct（执行）、**R**eflect（反思）。一个让 agent 从经验中学习的认知循环，而非盲目执行。

每个运维任务都遵循四阶段认知循环：

| 阶段 | 名称 | 目的 |
|------|------|------|
| **S** | 感知 | 从请求中提取关键信号 |
| **P** | 规划 | 召回过去的经验，选择策略 |
| **A** | 执行 | 执行选定的策略 |
| **R** | 反思 | 有效吗？下次记住什么？ |

**关键创新是 R 阶段（反思）：**

大多数 Agent 系统是 S→A（感知然后执行）——就像一个"失忆工人"，每次上班都忘记之前学到的一切。加入 Plan（召回过去的教训）和 Reflect（创建新教训）形成了一个**复利反馈循环**——agent 像一个"记笔记的工人"，每次任务后都变得更好。

## 总结：复合效应

七条原则相互增强：

```
原则 4（状态感知）+ 原则 6（Token 节约）
  → 只读变化的部分，用最便宜的方式读

原则 7（SPAR）+ 原则 5（时序管理）
  → 教训随时间积累，有生命周期管理

原则 1（Agent 手册）+ 原则 3（错误第一公民）
  → Agent 永远不会卡住；总是知道下一步做什么

原则 2（并行）+ 原则 4（增量）
  → 曾经需要几分钟的操作现在只需几秒
```

最终结果：一个**快速**（并行 + 增量）、**可靠**（错误处理 + 状态追踪）、**越用越聪明**（SPAR + 操作记忆）的 agent。
