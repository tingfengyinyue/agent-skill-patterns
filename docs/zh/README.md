# Agent Skill Patterns

[English Documentation](../../README.md)

构建能够**召回经验、按需加载知识并持续改进**的 AI Agent Skill。

---

## 为什么做这个项目？

大多数 AI Agent 的做法是把知识当作静态上下文——把一堆文档塞进 prompt 然后听天由命。当知识库增长到 context window 装不下时就会崩溃。

### 从我的实际痛点到可复用模式

这套架构最初由我设计，源于工作中的一个具体痛点：当我一次接手一批陌生项目时，需要在很短时间内理解代码结构、服务关系和历史背景，并快速定位、解决线上问题。传统方式需要反复翻阅代码、文档和历史记录，不仅耗时，而且同样的分析过程很难在下一次任务中复用。

为了解决这个问题，我开始设计并在日常工作中持续迭代这套工具：把操作流程写成 Skill，把服务、事件、Runbook 和经验教训组织为可关联的知识库，再通过 SPAR 和操作记忆让过去的排查经验能够被后续任务直接召回。

它不是只停留在文档中的设想。经过内部展示后，这套工具已被推荐到多个团队，在实际工作流中得到使用，也获得了使用者的积极反馈。

在平时的使用中，它主要带来了这些效果：

- 将反复出现的运维任务沉淀为可复用、执行方式一致的 Skill 工作流；
- 减少重复查找知识和无效加载上下文的成本；
- 将历史事件中的经验带入后续排查，避免重复走弯路；
- 让团队经验更容易分享、复用，并在持续使用中逐步改进。

本仓库提取的是可复用的架构与模式，不包含内部业务数据或特定环境配置。

本项目用三个架构创新解决了这个问题：

### 1. 漏斗式加载——只读需要的

Agent 不会读取整个知识库。先用索引过滤（开销极低），再按需深入命中的条目。

```
JSON 索引 (50 tokens) → 命中条目 (80 tokens) → 服务文档章节 (150 tokens)
         ↓ 过滤                ↓ 如需要                   ↓ 如需要
   95% 被排除            直接找到答案              加载完整上下文
```

**效果：** 典型加载 130-280 tokens，vs 朴素方式的 2000+。

### 2. 双向链接——任意方向导航

每个关系都存储在**两个端点**上。不管 Agent 在图中哪个位置，都能直接找到所有相关节点——无需扫描文件。

```
事件 → "Created OM: om-xxx"        (正向：学到了什么)
OM → "evidence.incidents: [...]"    (反向：为什么存在)
服务 A → "调用 服务 B"             (正向：依赖)
服务 B → "被 服务 A 调用"          (反向：被依赖)
```

### 3. 双向时序——过去指导未来

操作记忆（OM）是一个**时间桥梁**：它向后指向产生教训的事件，向前指向应该应用它的未来任务。

```
过去                           现在                         未来
[事件：发生了什么] → [OM：教训] → [下一个任务：召回并应用]
```

知识有生命周期：诞生（事件）→ 提炼（OM）→ 验证 → 久经考验 → 晋升为 runbook——或者证明无效后被废弃。

## 工作原理

### SPAR 认知循环

每个任务经历四个阶段——感知、规划、执行、反思：

```
会话 1: S → P(空)        → A         → R(创建 OM-001)
会话 2: S → P(召回 OM)   → A(更快)   → R(更新 OM-001)
会话 3: S → P(召回 OM)   → A(最优)   → R(无新内容)
```

关键洞察：**Plan** 召回过去的教训（防止重复犯错），**Reflect** 记录新的教训（为未来的 Plan 阶段提供输入）。这创造了一个复利反馈循环——Agent 每次任务后都变得更好。

→ [完整 SPAR 框架](spar-framework.md)

### 操作记忆

反思阶段的结构化输出。每条 OM 包含：

- **触发条件** —— 什么时候该召回这条教训（任务类型 + 服务 + 症状）
- **`better_action`** —— 下次该怎么做（祈使句、可操作）
- **可信度评分** —— low → medium → high（追踪可靠性）
- **命中计数** —— 被召回且有效的次数
- **生命周期** —— active → deprecated / superseded / graduated

→ [完整操作记忆规范](operational-memory-spec.md)

## 设计原则

七条原则指导本系统中每个 skill 的设计：

| # | 原则 | 摘要 |
|---|------|------|
| 1 | **Skill 是 Agent 手册，不是人类文档** | 显式触发条件、类型化参数、编号步骤、模板化输出 |
| 2 | **并行优先** | 独立步骤被显式标注为可并行 |
| 3 | **错误场景 = 第一公民** | 每个 skill 包含错误 → 解决方案表 |
| 4 | **状态感知：增量 > 全量** | 状态文件追踪进度；只处理增量 |
| 5 | **时序性知识管理** | 所有内容带时间戳、有生命周期管理、有过期检测 |
| 6 | **Token 节约架构** | JSON 索引、分层读取、优先级查询 |
| 7 | **分层处理 (SPAR)** | 感知 → 规划 → 执行 → 反思，让智慧持续积累 |

→ [设计哲学详解](design-philosophy.md) · [Token 节约策略](token-efficiency.md)

### Skill 模板

| 模板 | 做什么 | 核心特性 |
|------|--------|---------|
| **01 CLI 包装型** | 用自然语言接口包装 CLI 工具 | 优先级查询策略 |
| **02 文档维护型** | 代码变更 → 知识库文档自动同步 | 带状态文件的增量扫描 |
| **03 交叉验证型** | 跨多份文档检查一致性 | 双向依赖核对 |
| **04 工作流引擎型** | 状态机驱动的运维工作流 | 完整 SPAR 集成 + 任务路由 |
| **05 数据报表型** | 并行查询 → 增量计算 → 可视化 | 今日 vs 昨日 + 变化率 |
| **06 Code Health Review** | 从功能、架构、资源、稳定性和安全等维度审查整个仓库变更 | 独立维护者/攻击者审查 + 有限证据辩论 |

模板 06 提供英文运行手册 [SKILL.md](../../templates/06-code-health/SKILL.md) 和中文配套文档 [SKILL.zh-CN.md](../../templates/06-code-health/SKILL.zh-CN.md)。

已确认的 Review 漏检可以沉淀为本地私有、经过证据门控的经验，并在后续 Review 中召回；真实项目证据不会进入公开模板。

### 知识库架构

四层结构，详细程度递增、更新频率递减：

```
第 1 层: 服务文档   — 从代码自动生成（每周）
第 2 层: Runbook   — 人工编写的流程（按需）
第 3 层: 事件记录   — 每次事件的记录（按事件）
第 4 层: 操作记忆   — 有生命周期的经验教训（按任务）
```

→ [知识库架构详解](knowledge-base-architecture.md)

## 术语表

| 术语 | 含义 |
|------|------|
| **Token** | LLM 处理文本的基本单位。消耗越多 = 推理空间越小 |
| **Context window** | LLM 一次能"看到"的文本总量——像一张面积有限的书桌 |
| **Skill** | 结构化 Markdown 文件，精确告诉 AI Agent 如何完成特定任务 |
| **OM（操作记忆）** | 一条"经验教训"，包含触发条件、更好的做法和生命周期 |
| **SPAR** | 感知 → 规划 → 执行 → 反思。让 Agent 从经验中学习的认知循环 |
| **漏斗式加载** | 先用便宜索引过滤，只读命中的完整内容 |
| **双向链接** | 关系存储在两个端点上，任意方向可导航 |
| **时间桥梁** | OM 同时指向过去（证据）和未来（触发条件） |
| **晋升** | OM 可靠到足以被提升为正式 runbook |
| **可信度** | OM 可靠级别：low（新）→ medium（已验证）→ high（久经考验） |
