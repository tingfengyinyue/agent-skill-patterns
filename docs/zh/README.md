# Skill Patterns

一套经过生产环境验证的 AI Agent Skill 模式集合。

这些模式提取自一个真实的运维平台，其中 AI Agent 负责事件响应、服务监控、数据报表和跨服务验证——每天在生产环境中运行。

## 设计哲学

七条原则指导本集合中每个 skill 的设计：

| # | 原则 | 摘要 |
|---|------|------|
| 1 | **Skill 是 Agent 手册，不是人类文档** | 每个 skill 有显式触发条件、参数、编号步骤、机器可解析的结构 |
| 2 | **并行优先** | 可并发执行的步骤被显式标注 |
| 3 | **错误场景 = 第一公民** | 每个 skill 包含错误处理表 |
| 4 | **状态感知：增量 > 全量** | 状态文件追踪变化；只处理增量 |
| 5 | **时序性知识管理** | 所有知识带时间戳、有排序、有生命周期管理 |
| 6 | **Token 节约架构** | JSON 索引用于程序化召回；先读便宜的摘要再读昂贵的全文 |
| 7 | **分层处理流程 (SPAR)** | 感知 → 规划 → 执行 → 反思——一个让智慧持续积累的认知循环 |

→ [完整设计哲学文档](design-philosophy.md)

## Skill 模式模板

### 01 - CLI 包装型

将 CLI 工具（云平台 CLI、数据库客户端、日志查询工具）包装为：
- 自然语言接口
- 环境感知的配置映射
- 优先级查询策略
- 格式化输出 + 下一步建议

### 02 - 文档维护型

保持知识库文档与源代码同步：
- 增量扫描（只处理有新提交的仓库）
- Diff 路径 → 文档章节映射
- 状态文件追踪每个服务的最后扫描提交

### 03 - 交叉验证型

读取多份文档并交叉引用检查一致性：
- 接口存在性验证
- 双向依赖核对
- 孤儿检测（有生产者无消费者）

### 04 - 工作流引擎型

状态机驱动的运维工作流：
- SPAR 认知循环（感知 → 规划 → 执行 → 反思）
- 任务分类与路由
- 操作记忆的召回与创建
- 结构化输出格式

### 05 - 数据报表型

自动化数据采集、比较和可视化：
- 并行查询执行（今日 vs 昨日）
- 增量计算与变化率
- Canvas/可视化集成

## 核心创新：面向 Agent 的知识图谱

本架构最独特的特性——一个被设计为**可导航图**的知识库，具有三个关键属性：

### 1. 漏斗式按需加载——只读需要的

> Agent 不会读整个知识库。它先用索引过滤（开销极低），再按需深入读取命中的条目。

```
JSON 索引 (50 tokens) → 命中的 OM 条目 (80 tokens) → 服务文档章节 (150 tokens)
         ↓ 过滤                  ↓ 如需要                    ↓ 如需要
   95% 被排除            直接找到答案              加载完整上下文
```

典型知识加载量：**130-280 tokens**，vs 朴素方式的 2000+。索引就像目录——agent 读它来决定打开什么，而不是把所有东西都打开。

### 2. 双向链接——任意方向导航

> 每个关系都存储在**两个端点**上。不管 agent 在图中的哪个位置，都能直接找到所有相关节点——无需扫描文件。

```
事件 → "Created OM: om-xxx"        (正向：学到了什么)
OM → "evidence.incidents: [...]"    (反向：为什么存在)
服务 A → "调用 服务 B"             (正向：依赖)
服务 B → "被 服务 A 调用"          (反向：被依赖)
```

### 3. 双向时序——过去指导未来

> OM（操作记忆）是一个**时间桥梁**：它向后指向产生教训的事件，向前指向应该应用它的未来任务。

```
过去                           现在                         未来
[事件：发生了什么] → [OM：教训] → [下一个任务：召回并应用]
    evidence.incidents ──▶       ◀── trigger.symptoms 匹配
```

知识有生命周期：诞生（事件）→ 提炼（OM, 低可信度）→ 验证（中）→ 久经考验（高）→ 晋升为 runbook 或废弃。

## 操作记忆系统

通过 SPAR 反思阶段实现**从经验中学习**的 Agent。

每次任务完成后问四个问题：
1. 走了弯路吗？
2. 比上次更快了吗？
3. 遇到意外陷阱了吗？
4. 能提炼出"下次做 X"的规则吗？

如果有 → 创建一条操作记忆，包含：
- 触发条件（任务类型、服务、症状）
- 之前哪里出了错（`context_before`）
- 下次该怎么做（`better_action`）
- 可信度评分（low → medium → high）
- 命中计数（使用频率）
- 生命周期管理（active → deprecated → superseded → graduated）

→ [完整操作记忆规范](operational-memory-spec.md)

## 元模式

从所有操作记忆中观察到的两个反复出现的策略：

> **先做最便宜的确定性验证；把昂贵的全局搜索推到最后。**

> **API 返回空不代表数据不存在——换个维度查询试试。**

## 术语表

| 术语 | 含义 |
|------|------|
| **Token** | LLM 处理文本的基本单位。消耗越多 = 推理空间越小。想象成"书桌面积" |
| **Context window** | LLM 一次能"看到"的文本总量——像一张面积有限的书桌 |
| **Skill** | 一个结构化的 Markdown 文件，精确告诉 AI Agent 如何完成特定任务 |
| **OM（操作记忆）** | 一条"经验教训"——记录之前做错了什么、下次该怎么做 |
| **SPAR** | 感知 → 规划 → 执行 → 反思。让 Agent 从经验中学习的认知循环 |
| **漏斗式加载** | 读取策略：先用便宜的索引过滤，只读命中的完整内容 |
| **双向链接** | 每个关系存储在两个端点上，任意方向都能直接导航 |
| **时间桥梁** | OM 的独特属性：同时指向过去（证据）和未来（触发条件） |
| **晋升** | 当一条 OM 可靠到足以被提升为正式 runbook |
| **废弃** | 当一条 OM 失败次数足够多，不再可信 |
| **元模式** | 跨多条 OM 出现的策略——"模式的模式" |
| **命中** | OM 被成功召回并应用一次（追踪有多有用） |
| **可信度** | OM 的可靠级别：low（新）→ medium（已验证）→ high（久经考验） |
