# SPAR 框架

面向 AI Agent 运维任务的四阶段认知循环。

SPAR 代表 **Sense（感知）→ Plan（规划）→ Act（执行）→ Reflect（反思）**。它将 agent 从无状态的执行器（每次任务后就忘记一切的"失忆工人"）转变为能够持续积累运维智慧的学习系统。

---

## 为什么需要 SPAR？

大多数 AI Agent 工作流是两阶段的：理解请求，然后执行。这对简单任务有效，但对运维工作来说会失败，因为：

- 同类问题会反复出现，但每次有细微变化
- 过去的经验包含关键的捷径
- 错误代价高昂，绝不能重复犯
- 知识必须跨会话积累

SPAR 增加了两个阶段来创建反馈循环：
- **Plan** = 回忆过去什么有效（防止重复犯错）
- **Reflect** = 记录学到了什么（为未来的 Plan 阶段提供输入）

```
会话 1: S → P(空) → A → R(创建 OM-001)
会话 2: S → P(召回 OM-001) → A(更快) → R(更新 OM-001)
会话 3: S → P(召回 OM-001, 高可信度) → A(最优) → R(无新内容)
```

## 四个阶段

### S 阶段——感知

**目的：** 从非结构化请求中提取结构化信号。

**动作：**
1. 识别任务类型（事件响应 / 批量操作 / 数据查询 / 配置变更 / 审计）
2. 从上下文中提取服务名
3. 提取错误信息、用户标识、时间戳
4. 确定环境（测试 / 预发 / 生产）

**输出：** 对"需要做什么"的结构化理解。

```markdown
任务: 事件响应
服务: payment-service
错误: "timeout after 9s on /api/order/create"
用户: uid-12345
环境: 生产
时间: 2026-07-15 14:30
```

### P 阶段——规划

**目的：** 召回过去的经验，选择执行策略。

**动作：**
1. **第一件事：召回操作记忆（OM）**
   - 按 task_type + service + symptoms 过滤
   - 读取匹配条目的 `better_action` 字段
   - 决定是否采用过去的教训
2. 如有需要，查阅相关 runbook
3. 制定执行计划

**关键规则：** Plan 阶段**必须**以记忆召回开始。即使目前还没有任何记忆（例如某个新服务的第一次任务），召回动作也必须执行——这是系统从第一天就开始学习的基础。

**召回方法：**
```
1. 读取 index.md 的 JSON 块
2. 过滤: task_type 包含 "incident" 且 services 包含 "payment"
3. 匹配 symptoms: "timeout" 出现在 om-001 中
4. 读取 om-001 完整条目 → better_action 说"先检查行锁"
5. 计划: 从行锁检查开始，而不是泛泛的日志搜索
```

### A 阶段——执行

**目的：** 执行计划。这是真正干活的阶段。

**动作因任务类型而异：**

| 任务类型 | 典型执行内容 |
|---------|------------|
| 事件响应 | 查询日志 → 分析 → 定位代码 → 生成报告 |
| 批量操作 | 下载数据 → 验证 → 生成脚本 → 风险评估 |
| 数据查询 | 构建 SQL → 执行 → 格式化结果 |
| 配置变更 | 查询当前状态 → 生成变更命令 → 风险评估 |

**执行期间的关键原则：** 遵循优先级查询策略。

```
优先级 1: 最便宜的确定性验证（trace_id、具体 ID）
优先级 2: 范围化查询（路径 + 时间窗口）
优先级 3: 过滤式广泛查询（错误级别 + 服务名）
优先级 4: 昂贵的全局搜索（全文搜索、用户 ID）
```

### R 阶段——反思

**目的：** 记录学到的教训。这个阶段是**强制的**——永远不能跳过。

**四个问题：**

每次任务完成后，问自己：

1. **走了弯路吗？**（找到正确路径之前走了错误路径）
2. **比上次更快了吗？**（还是更慢了——退步了？）
3. **遇到意外陷阱了吗？**（会让未来的 agent 也踩坑的东西）
4. **能提炼出"下次做 X"的规则吗？**（可操作的改进）

**如果任何一个答案是"是"** → 创建一条操作记忆（OM）条目。

**反思输出：**
```markdown
Applied: om-2026-04-23-001 (使用了行锁检查捷径——节省 5 分钟)
Memorized: om-2026-07-15-001 (新: 批量模式下的支付超时需要先检查队列深度)
```

## 任务分类与路由

```
┌─────────────────────────────┐
│         S（感知）            │
│  提取: 类型、服务、          │
│  错误、用户、环境            │
└─────────────┬───────────────┘
              │
              ▼
┌─────────────────────────────┐
│         P（规划）            │
│  1. 召回 OM                 │
│  2. 查阅 runbook            │
│  3. 选择策略                │
└─────────────┬───────────────┘
              │
    ┌─────────┼─────────┬──────────┐
    ▼         ▼         ▼          ▼
┌───────┐ ┌───────┐ ┌───────┐ ┌───────┐
│ A1:   │ │ A2:   │ │ A3:   │ │ A4:   │
│事件   │ │批量   │ │配置   │ │查询   │
└───┬───┘ └───┬───┘ └───┬───┘ └───┬───┘
    └─────────┴─────────┴──────────┘
              │
              ▼
┌─────────────────────────────┐
│         R（反思）            │
│  4 个问题 → 创建 OM         │
│  标签: Applied / Memorized  │
└─────────────────────────────┘
```

## 与操作记忆的集成

SPAR 的力量来自它与操作记忆系统的紧密耦合：

| SPAR 阶段 | OM 交互 |
|-----------|---------|
| **Plan** | 读取：召回相关记忆，应用 `better_action` |
| **Act** | 引用：按照召回的记忆中的策略执行 |
| **Reflect** | 写入：创建新记忆，更新命中次数 |

**生命周期关联：**
- 记忆被召回且有效 → `hits + 1`，`confidence` 可能升级
- 记忆被召回但无用 → 在反思中记录，可能降级
- 记忆 6 个月未被召回 → 标记为过期

## 完整 SPAR 循环示例

**用户请求：** "payment-service 线上报 timeout，用户 uid-12345 下单失败"

### S（感知）
```
任务类型: 事件响应
服务: payment-service
症状: timeout
用户: uid-12345
接口: 下单
环境: 生产
```

### P（规划）
```
1. 召回 OM: 找到 om-2026-04-23-001
   - "支付超时 → 先检查行锁，再做广泛日志搜索"
   - 可信度: medium, 命中次数: 3
2. 计划:
   步骤 1: 从网关日志获取 trace_id（最便宜的确定性查询）
   步骤 2: 检查行锁竞争（来自 OM 建议）
   步骤 3: 如果不是锁 → 扩大到全面日志分析
```

### A（执行）
```
1. 用 uid-12345 查询网关日志 → 找到 trace_id: abc-123
2. 用 trace_id 查询 payment-service → 发现 "lock wait timeout"
3. 确认: orders 表在并发批量插入期间有行锁竞争
4. 根因: 批量任务未使用行级隔离
5. 生成报告：包含代码位置和修复建议
```

### R（反思）
```
Q1: 走了弯路吗？否——OM 的捷径完美有效
Q2: 比上次更快了吗？是——跳过了 5 分钟的泛泛日志搜索
Q3: 意外陷阱？是——批量任务 14:30 运行，正好是下单高峰
Q4: "下次做 X"的规则？是——"支付超时在 14:xx → 先检查批量任务时间冲突"

→ 创建: om-2026-07-15-001 (批量时间冲突模式)
→ 更新: om-2026-04-23-001 (hits: 4, 仍然有效)

输出标签: Applied: om-2026-04-23-001 | Memorized: om-2026-07-15-001
```

## 实施要点

### 强制反思阶段

反思阶段是最容易被跳过的（"任务做完了，何必再想？"）。强制执行的方法：

1. **输出格式要求它** —— 每个 skill 的输出模板都包含 `Applied:` 和 `Memorized:` 字段
2. **4 个问题是清单** —— 即使 4 个回答都是"否"也是有效的反思（说明执行已经是最优的）
3. **反思产生可见产物** —— 知识库中的 OM 文件就是反思的证据

### SPAR vs 简单 Agent 对比

| 特性 | 简单 Agent | SPAR Agent |
|------|-----------|------------|
| 记忆 | 无（每次任务后遗忘） | 操作记忆跨会话持久保存 |
| 学习 | 无 | 可信度评分 + 命中计数追踪可靠性 |
| 策略 | 每次都用相同方法 | 根据过去经验自适应 |
| 错误 | 可能无限重复同样的错误 | 通过 OM 召回显式防止重犯 |
| 速度 | 恒定（不会提升） | 随时间提升（捷径不断积累） |
