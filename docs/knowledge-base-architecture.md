# Knowledge Base Architecture

A multi-layer knowledge system designed for AI agent consumption with minimal token cost.

---

## Overview

The knowledge base organizes operational knowledge into four distinct layers, each with a different update frequency, access pattern, and lifecycle:

```
knowledge-base/
├── services/              # Layer 1: Service documentation (auto-generated)
├── runbooks/              # Layer 2: Procedural knowledge (manually authored)
├── incidents/             # Layer 3: Event records (created per-event)
├── memory/operational/    # Layer 4: Lessons learned (SPAR Reflect output)
└── .service-scan-state.json  # State tracking
```

---

## Layer 1: Service Documentation

**Update frequency:** Weekly (triggered by code changes)
**Author:** Auto-generated by the doc-maintainer skill
**Purpose:** Canonical reference for each service's APIs, data models, dependencies

### Structure per service file

```markdown
---
type: service
tags: [service]
aliases: ["payment-service"]
repo: "<git-repo-url>"
module: "<module-path>"
database: "<db-name>"
last_scan: "2026-07-15"
---

| Method | Path | Handler | Description |

## Message Queue
| Role | Topic | Description |
|------|-------|-------------|
| Producer | order.created | Emitted after successful order creation |
| Consumer | payment.confirmed | Processes payment confirmations |

## Scheduled Tasks
| Schedule | Task | Description |
|----------|------|-------------|
| */5 * * * * | SyncOrderStatus | Sync pending orders with payment gateway |

---

## Related Operational Memory
(auto-populated query)

## Related Incidents
(auto-populated query)
```

### Key design decisions

- **Frontmatter** enables programmatic queries (filter by type, database, etc.)
- **Dependencies are bidirectional** — both "I call X" and "X calls me" recorded
- **Auto-generated sections** are clearly separated from manual annotations
- **Related sections** at the bottom auto-populate via query/link mechanisms

## Layer 3: Incident Records

**Update frequency:** Per-event (created when incidents occur)
**Author:** Generated by the workflow-engine skill
**Purpose:** Historical record of what happened, when, and how it was resolved

### Naming convention

```
incidents/YYYY-MM-DD-<service>-<slug>.md
```

### Incident template

```markdown
---
date: 2026-07-15
service: payment-service
severity: high
status: resolved
tags: [incident]
---

# 2026-07-15 payment-service Order Timeout

## Basic Info
- **Time:** 2026-07-15 14:30 - 14:45
- **Service:** payment-service
- **Interface:** POST /api/order/create
- **Affected users:** ~200 users during 15-min window
- **Error:** "lock wait timeout exceeded"

## Symptoms
Users reported order creation hanging for 9+ seconds then failing.

## Timeline
| Time | Event |
|------|-------|
| 14:30 | Batch import cron job started |
| 14:32 | First timeout errors in logs |
| 14:35 | Alert triggered |
| 14:38 | Root cause identified (table lock from batch job) |
| 14:40 | Batch job killed |
| 14:42 | Service recovered |
| 14:45 | Confirmed all clear |

## Root Cause
Daily batch import job (14:30 cron) acquired table-level lock on orders table,
blocking all concurrent INSERT operations.

## Fix
1. Immediate: killed batch job process
2. Permanent: changed batch job to use row-level locks with batched inserts

## Lessons & Improvements
→ Created OM: om-2026-07-15-001 (check batch schedule on payment timeouts)
→ Action item: move batch job to 03:00 off-peak window

## Relations
**Service:** [payment-service](../services/payment-service.md)
**OM:** [om-2026-07-15-001](../memory/operational/om-2026-07-15-001-batch-schedule-conflict.md)
```

## Layer 4: Operational Memory

See [Operational Memory Specification](operational-memory-spec.md) for the complete spec.

**Key point here:** OM is the only layer that has a **lifecycle** (confidence scoring, hit counting, deprecation, graduation). Other layers are either static (runbooks), auto-generated (services), or append-only (incidents).

## Access Patterns (Token Efficiency)

The layers are designed for a specific read order that minimizes token consumption:

```
Query arrives
    │
    ▼
┌─────────────────────────────────┐
│ 1. Read OM index.md JSON block  │  ~50 tokens
│    (programmatic filter)        │
└───────────────┬─────────────────┘
                │ Found relevant OM?
    ┌───────────┼───────────────┐
    │ YES       │               │ NO
    ▼           │               ▼
┌──────────┐    │    ┌─────────────────────┐
│ Read OM  │    │    │ 2. Read service doc │  ~300 tokens
│ better_  │    │    │    (relevant section)│
│ action   │    │    └──────────┬──────────┘
│ ~100 tok │    │               │
└──────────┘    │               ▼
                │    ┌─────────────────────┐
                │    │ 3. Read runbook     │  ~200 tokens
                │    │    (if needed)      │
                │    └──────────┬──────────┘
                │               │
                └───────────────┘
                        │
                        ▼
              ┌─────────────────────┐
              │ 4. Search incidents │  only if pattern
              │    (only if needed) │  matching needed
              └─────────────────────┘
```

**Total typical read:** 150-500 tokens for context loading, vs 2000+ if reading everything.

## Cross-Referencing

All layers reference each other:

| From | To | Link Type |
|------|----|-----------|
| Incident → Service | `[payment-service](../services/payment.md)` | Which service was affected |
| Incident → OM | `Created OM: om-xxx` | What was learned |
| OM → Incident | `evidence.incidents: [...]` | What event triggered this lesson |
| Service → OM | "Related Operational Memory" section | Lessons about this service |
| OM → Runbook | `better_action` references procedures | "See runbook X for details" |

## State Tracking

The `.service-scan-state.json` file tracks incremental state:

```json
{
  "last_scan": "2026-07-15T10:30:00+08:00",
  "services": {
    "payment-service": {
      "last_commit_sha": "abc123def456",
      "last_scan": "2026-07-15",
      "sections_updated": ["api_endpoints", "data_models"]
    },
    "auth-service": {
      "last_commit_sha": "789ghi012jkl",
      "last_scan": "2026-07-10",
      "sections_updated": []
    }
  }
}
```

**Purpose:** The doc-maintainer skill reads this file to determine which services need re-scanning (only those with new commits since `last_commit_sha`).
