# Code Health Review

## 目标

以整个项目的维护者、架构师和线上负责人视角审查代码变更，而不是只对 Diff 逐行挑错。

先理解项目目标、仓库规则、模块边界、调用关系和运行时资源，再判断本次变更是否正确、整洁、可维护、稳定且可验证。

这个 Skill 只负责 Review，不自动修改代码、创建任务、批准合并或执行生产操作，除非用户明确要求。

## 核心原则

- 不能只看 Diff；还要读取需求、Issue、包围函数/类、仓库规则、调用方、被调用方和测试上下文。
- 每个 Review 结论必须有证据、项目内的影响说明和可验证的下一步。
- 确定性工具负责提供事实，Agent 负责跨需求、架构和运行时行为进行综合判断。
- 两个 Agent 的一致意见不等于事实，尤其不能替代高风险变更的人工审批。
- 完整检查链路：需求 → 入口 → 数据/状态流 → 副作用 → 失败/重试/取消 → 监控 → 测试 → 回滚/兼容性。
- 将代码书写质量和代码腐烂（Code Rot）视为同一个可维护性维度：既检查本次代码现在是否能工作，也检查它是否让仓库更难理解、更难测试和更难修改。

## 必要输入

需要识别：

1. repo_path：仓库绝对路径；
2. fixed_point：目标分支、merge-base、commit、tag 或 HEAD~N；
3. spec_source：Issue、PRD、任务、验收标准，或明确说明没有需求文档。

先固定并验证参考点：

    git -C <repo_path> rev-parse <fixed_point>
    git -C <repo_path> diff --stat <fixed_point>...HEAD
    git -C <repo_path> log --oneline <fixed_point>..HEAD

参考点无效或 Diff 为空时停止。保留用户已有的未提交改动，不使用破坏性 Git 命令。

## 全局 Review 流程

### 1. 先建立项目地图

优先读取：

- AGENTS.md、CLAUDE.md、CONTRIBUTING.md、编码规范、ADR 和架构文档；
- 包管理文件和 lockfile；
- CI、Makefile、任务脚本、测试配置和部署清单；
- 入口、路由/Controller、Worker、Repository、共享库和领域边界；
- 已有测试、压测和 Profiling 脚本。

如果项目已经被代码知识图谱索引，优先使用：

    codebase-memory-mcp cli list_projects
    codebase-memory-mcp cli get_architecture '{"project":"<name>"}'
    codebase-memory-mcp cli detect_changes '{"project":"<name>"}'

对重要变更符号使用双向 trace_path，查看调用方和被调用方。图谱过期时必须说明，并回退到代码和测试检查。

### 2. 还原需求和系统链路

内部先写出类似下面的链路：

    用户/事件 → 入口 → Service/Agent → 状态/数据存储 → 外部副作用
              → 成功 / 失败 / 重试 / 取消
              → 日志指标追踪 → 测试或运维验证

给每个变更文件分类：API、领域逻辑、编排、持久化、传输、共享库、UI、Worker、配置、测试、迁移或部署。

没有需求文档时，不要自行发明需求。将功能正确性标记为“意图无法完全验证”，但继续检查安全性、兼容性和回归风险。

### 3. 判断影响范围和风险

记录：

- 直接影响：修改的函数、类、路由、Schema、配置和测试；
- 间接影响：调用方、实现方、共享工具、数据模型、Worker 和客户端；
- 状态影响：数据库、缓存、队列、文件、Session、凭证和浏览器状态；
- 资源影响：内存、CPU、IO、网络、Goroutine/Task、连接池和模型 Token；
- 运维影响：部署顺序、迁移、回滚、Feature Flag、告警和兼容性。
- 可维护性影响：复杂度堆积、重复实现、死代码/废弃路径、变更热点、测试腐烂和架构漂移。

严重级别：

- P0：安全、数据丢失/损坏、宕机、越权或无界资源增长；
- P1：明确的线上 Bug、契约破坏、错误业务行为或关键失败路径缺失；
- P2：维护性、性能、测试、可观测性或兼容性风险；
- P3：局部清理和非阻塞改进。

同时标记置信度：confirmed、high、medium、needs-runtime-verification。

### 4. 两个 Agent 独立审查

两个 Agent 接收相同的项目地图、Diff、需求、图谱上下文和测试事实，但首轮不能看到彼此的结论。

维护者 Agent 重点检查：

- 功能和需求覆盖；
- 代码书写质量、整洁度、可维护性、YAGNI 和现有 Code Rot 基线；
- 架构、契约、调用方和下游影响；
- 测试、监控、发布和兼容性。

攻击者 Agent 重点检查：

- 非法输入、部分失败、超时、重试、取消和重复执行；
- 内存/资源所有权、无界增长、连接/Task/句柄释放和背压；
- 权限、凭证、沙箱、Prompt/Tool 输入和数据泄露；
- 并发、数据一致性、回滚和运维故障。

每个 Agent 必须输出：候选问题、证据、因果链、后果、严重级别、置信度、最小验证方式，以及已经检查且确认正常的路径。

### 5. 只对高价值分歧进行辩论

不要让两个 Agent 对所有风格意见进行无限讨论。只辩论：

- 一方判定 P0/P1、另一方拒绝或明显降级的问题；
- API、数据、架构边界、资源生命周期和安全后果的分歧；
- 会改变合并结论或需要较大运行成本验证的 P2 分歧。

最多两轮、最多八个分歧包，不使用多数投票。

每个分歧必须回答：

    结论：
    证据位置：
    完整调用路径：
    项目影响：
    对方观点哪里不成立：
    需要什么验证：

如果仍然不能确定，降级为 needs-runtime-verification，并设计最小的区分性测试。

### 6. 通过项目健康度维度审查

至少覆盖：

- 功能和需求；
- 代码整洁度和可维护性；
- 架构边界和全局调用影响；
- 测试；
- 稳定性和可靠性。

代码书写质量和 Code Rot 必须一起检查：

- 复杂度是否继续堆积：过长函数、深层分支、隐式状态和多处转换；
- 是否出现重复或平行实现，并且未来可能发生行为漂移；
- 是否留下未使用符号、失效配置、注释代码、长期 TODO/FIXME/HACK、废弃兼容层或已弃用依赖；
- 是否修改了高变更热点，却没有降低复杂度、补齐测试或明确清理边界；
- 测试、日志、指标和文档是否已经落后于真实行为；
- 结论必须至少有两个相互独立的迹象，或一个强迹象加上具体维护后果。不能仅凭“看起来乱”就判定代码腐烂；
- 明确区分变更之前就存在的腐烂、此次变更新增的腐烂，以及此次变更是否改善了原有问题。

仓库存在 Git 历史时，运行：

    python3 scripts/analyze_code_rot.py <repo_path> --since-days 180 --output /tmp/code-rot-report.md

该脚本只提供复杂度代理指标、标记数量和变更热点候选，不直接宣判死代码或复杂度问题；候选热点必须结合调用关系、测试和仓库规则复核。

根据风险再加入：

- 内存和资源生命周期；
- 性能和数据访问；
- 并发和取消；
- 安全和数据边界；
- 可观测性和发布运维。

内存和性能问题必须区分：

- confirmed：已有测试、Profiling 或明确的边界证明；
- high：根据真实代码路径可以高度推断；
- needs-runtime-verification：需要依赖流量、数据规模、框架行为或部署配置验证。

### 7. 运行针对性验证

只运行仓库中已定义的、与变更相关的非生产检查。说明哪些检查没有运行。

典型验证包括：

- Python：pytest、ruff、pyright、异步测试；
- TypeScript：包级类型检查、Lint、契约测试和目标 E2E；
- Go：go test、go vet、竞态测试和已配置的 golangci-lint；
- 资源问题：已有 Benchmark、压测、tracemalloc、memray、pprof 或 Node Heap 工具。
- Code Rot：运行 `scripts/analyze_code_rot.py`，再用调用关系、测试和本地规则复核热点。

不自动运行生产验证、破坏性迁移、真实数据修复或真实外部副作用。

### 8. 输出全局 Review 报告

报告顺序：

1. 结论：BLOCK、CONCERNS 或 PASS WITH NOTES；
2. 执行摘要；
3. 变更地图；
4. 维护者 Agent 的独立结论；
5. 攻击者 Agent 的独立结论；
6. 分歧辩论结果；
7. 按严重级别排序的问题；
8. 未执行的测试、Profiling 和运维验证；
9. 已确认正常的关键路径；
10. 未解决的问题和假设。

不要把 P0/P1 隐藏在很长的检查清单中。不要把两个 Agent 的一致意见当成证据。

## 非目标

普通 PR 不自动启动完整的全库审计流水线，不自动创建 Linear 任务，不自动修改源码，也不替用户做最终合并决定。
