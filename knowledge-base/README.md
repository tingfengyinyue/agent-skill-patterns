# Knowledge Base Scaffold

This is a ready-to-use knowledge base structure. Fork it, fill in your service details, and start building operational memory.

## Quick Start

1. Copy this `knowledge-base/` directory into your project
2. Fill in `services/` with your service documentation (use `services/_template.md`)
3. Configure your workflow-engine skill to point at this directory
4. Start working — the SPAR Reflect phase will populate `memory/operational/` automatically

## Directory Structure

```
knowledge-base/
├── services/                    # Service documentation (auto-generated)
│   └── _template.md            # Template for new service docs
├── incidents/                   # Event records (per-incident)
│   └── _template.md            # Template for incident records
├── memory/
│   └── operational/             # Operational Memory entries
│       ├── index.md             # Master index with JSON recall block
│       └── _template.md        # Template for new OM entries
├── runbooks/                    # Procedural knowledge
│   └── _template.md            # Template for runbooks
└── .service-scan-state.json    # State tracking for doc-maintainer
```

## How It Works

1. **Service docs** are auto-generated by the doc-maintainer skill (scan code → write docs)
2. **Incidents** are created by the workflow-engine skill when issues are reported
3. **Operational Memory** is created by the SPAR Reflect phase after every task
4. **Runbooks** are manually authored, or graduated from high-confidence OM entries
5. **State file** tracks incremental progress to avoid redundant work

## Token-Efficient Access Pattern

```
Agent receives task
  → Read memory/operational/index.md JSON block (~50 tokens)
  → Filter relevant memories
  → Read matched OM entries (~100-200 tokens each)
  → If needed: read service doc for context (~300 tokens)
  → If needed: consult runbook (~200 tokens)
```

Total typical context load: 150-500 tokens.
